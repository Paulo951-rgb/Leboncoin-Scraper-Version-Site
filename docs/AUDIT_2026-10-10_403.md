## 3. Régressions CONFIRMÉES

### R1 — Effondrement de la protection anti-débit (gravité : élevée)

**Preuve historique** : `a861165` « restore fast parallel scraping mode »
- `concurrency` 5→10, puis presets **10 / 15 / 25**
- `minDelayMs` **1500→500**, puis presets **500 / 200 / 50**

**Preuve code** (`rateLimiter.js`) : le limiteur utilise `baseDelayMs` comme
délai *minimal* :

```js
this.baseDelayMs = opts.baseDelayMs ?? 800;
this.minDelayMs = opts.minDelayMs ?? 300;   // ← non fourni par l'appelant
...
this._currentDelay = this.baseDelayMs;      // démarre au minimum
```

Et `DescriptionEnricher` instancie :

```js
new AdaptiveRateLimiter({ baseDelayMs: opts.minDelayMs || 800, maxDelayMs: opts.maxDelayMs || 8000 })
// opts.minDelayMs vaut le preset (500/200/50), opts.maxDelayMs (1000/600/300)
```

**Conséquence mesurée** (commande exécutée) :

```
moyen          base 500   max 1000  backoff après 1 blocage = 1000ms
rapide         base 200   max 600   backoff = 400ms
ultra-rapide   base 50    max 300   backoff = 100ms
```

Le backoff après blocage est donc **≤ 1 s** (et 100 ms en ultra-rapide) : aucune
réduction de cadence réelle → le serveur limite toujours plus fort.

**Correctif** :
- presets durcis → concurrence **8 / 10 / 12**, délais de base **1500 / 1000 / 700**,
  max **4000 / 3000 / 2500** ;
- backoff **agressif dès le premier blocage** : `base × 2^max(N,4)` (soit ×16),
  donc plusieurs secondes de pause immédiate ;
- `Retry-After` appliqué comme **pause inter-batch** `max(délai adaptatif, Retry-After)`.

### R2 — Compteurs de session faux (gravité : moyenne)

**Preuve code** (`ipcHandlers.js`) :
```js
const adsMatch = msg.match(/(\d+)\s+annonce\(s\)\s+(?:unique|extrait)/i);
```
vs ligne réellement émise par le pipeline :
```js
logger.info(`Étape HAR -> Annonces terminée : ${ads.length} annonces extraites.`);
```

**Preuve exécutée** :
```
"Étape HAR -> Annonces terminée : 236 annonces extraites." => false
"[mergeDuplicates] … 236 unique(s) en sortie."              => false
```
Le motif n'exige jamais le pluriel → `adsFound` restait à `0` (d'où « 236
extraites / 0 trouvée »). Le compteur de doublons cumulait en outre `+=` (double
comptage possible).

**Correctif** : nouveaux motifs (`annonces? extraites?`, `unique\(s\) en sortie`),
doublons idempotents (`Math.max`), ligne `[METRICS]` émise par le pipeline,
libellés du résumé clarifiés.

## 4. Diagnostic 403 (instrumentation sûre)

Instrumentation ajoutée **sans journaliser aucun secret** :

- Chaque requête d'enrichissement reste dans le **contexte Playwright prévu**
  (fetch in-page héritant cookies + UA) — confirmé par lecture.
- La ligne `[METRICS] Descriptions : …` agrège : enrichies / absentes / bloquées
  (403/429) / erreurs HTTP / **non traitées** — pour distinguer « 80 récupérées »
  de « 156 en attente ».
- Les blocages journalisent l'URL tronquée, le statut et un code structuré
  (`[HTTP_ACCESS_REFUSED]`, `[HTTP_RATE_LIMITED]`) — **jamais** les cookies,
  jetons ou en-têtes sensibles.

Conclusion du diagnostic : les 403 apparaissent par **rafale** après une série de
succès → signature de **rate-limit** (R1), pas de session corrompue.

## 5. Résultats partiels & interface (vérifié)

- `writeOutputs(ads)` est appelé **avant** l'enrichissement, périodiquement
  (`done % 10` et à la fin), et **avant** chaque recyclage de contexte.
- Sur arrêt 403/429 : exit code **3** (403) / **4** (429) ; `ipcHandlers` émet
  `state: 'partial'` (jamais `completed`), avec `adsKept`.
- Le renderer (`scraperModule`) traite `partial` comme terminal → boutons
  réactivés, nouvelle tâche possible.
- Reprise : `annonces.json` déjà présent + `fresh=false` → reprise sans
  re-scraping (le job relance toutefois `fresh: true` ; la reprise manuelle
  reste possible via le pipeline).

## 6. Non concluant / limites (honnêteté)

- **Aucune preuve** d'une fuite de cookies, d'un mélange de domaines ou d'une
  fermeture prématurée de contexte : ces pistes ont été **examinées et écartées**.
- Le UA est bien propagé : piste écartée.
- Les tests utilisent des réponses simulées : **aucun test réel contre Leboncoin**
  n'a été effectué (interdit ici). Le comportement réel du serveur (durée et
  seuil exacts du rate-limit) ne peut donc pas être mesuré dans cet environnement.
- Le déclencheur « 80 descriptions » n'est pas une constante codée en dur ; la
  séquence dépend du serveur. Impossible de la reproduire hors ligne.
